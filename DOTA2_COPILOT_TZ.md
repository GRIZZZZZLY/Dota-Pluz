# Техническое задание: Dota 2 Copilot (Jev + Groq + DeepSeek)

**Версия ТЗ:** 1.0 · 6 ноября 2026  
**Назначение:** документ для coding-агента (Claude Code / Codex / аналог).  
**Платформа MVP:** Windows 10/11, Dota 2 через Steam, два монитора; интерфейс и отчёты на русском.  
**Подход:** fork-first, reuse-first, offline-first; облачные модели необязательны.

## 0. Главная инструкция coding-агенту

Создай работающее локальное приложение **Dota 2 Copilot**, которое собирает разрешённую телеметрию, распознаёт видимые пики, выдаёт объяснимые рекомендации героев, предметов, прокачки и талантов, записывает собственные рекомендации и после матча анализирует повторяющиеся ошибки игрока. **Не пиши приложение с нуля.** Возьми **v2** репозитория `Tajaddin/dota2-build-generator` как базу, сохраняй его тесты и рабочие возможности, остальные проекты подключай как небольшие адаптеры. Делай вертикальные рабочие срезы, каждый со своими тестами. Не делай большой переписи всех модулей сразу. Не предполагается, что пользователь предоставит Steam-логин или API-ключи в исходниках.

**Важное ограничение:** в обычных матчах приложение работает только как read-only помощник. Не внедрять DLL, не читать память игры, не автоматизировать клавиатуру/мышь, не изменять файлы/конфиги Dota кроме разрешённого GSI-config, не имитировать команды прокачки, покупки и боевых действий. Автодействия для управления **Lua-ботами**, если когда-либо понадобятся, реализовать только как отдельный эксперимент для разрешённого локального лобби, никогда не смешивать с кодом пользовательского матчмейкинга. Официальный GSI — интерфейс **получения** состояния, а не API для действий. Наличие оверлея не означает одобрение Valve. Учитывать Steam Subscriber Agreement: https://store.steampowered.com/agreement/.

## 2. Продукт, цели и границы

**Цель:** персональный интеллектуальный тренер, который помогает: (1) выбирать героя на драфте, (2) понимать следующую способность/талант, (3) выбирать основной и ситуационный предмет с учётом угроз и золота, (4) анализировать собственную игру с доказательствами и составлять план улучшения. Агент не перемещает героя, не кастует и не фармит за игрока.

**Не входит в MVP:** управление персонажем; автоматическая установка скиллов и покупка через внешние нажатия; чтение невидимой информации о врагах; распознавание приватного тумана войны; античит-обходы; собственное обучение LLM; мультиплеерный облачный сервис, Steam OAuth; полноценный локальный парсер реплеев; гарантии повышения MMR.

**Разрешённая альтернатива Quickbuy:** приложение рекомендует предмет, показывает стоимость/компоненты и действие, которое игрок выполняет сам в магазине. Можно предложить включить штатный функционал Dota 2 Mark for Buy/автопокупку помеченных предметов, но **не выполнять внешние клики по игровому интерфейсу**. Никаких обещаний, что GSI сможет редактировать Quickbuy.

**Платформа:** сначала Windows 10 Pro/11, два монитора, Dota Borderless; поддержать 1080p и 1440p, нетребовательный режим второго экрана. Интерфейс локальный, русский, с тёмной темой. Английские оригинальные названия предметов/героев допустимы, справка на русском.

## 3. Технологический стек (преимущественно уже есть)

- Backend: Python **3.12** + `uv`, `FastAPI`, `Pydantic v2`, `httpx`, `Typer`, `uvicorn` из d2bg v2; асинхронные HTTP-клиенты провайдеров.
- Frontend: React 19 + TypeScript + Vite из `web/` d2bg. Не создавать новый SPA с нуля. В первую очередь использовать страницу `/compact` на втором мониторе.
- Драфт CV: `mss`, `OpenCV`, `numpy` из Dota Assist как опциональный модуль; запускать захват только во время экрана драфта, отображать уровень уверенности, разрешать ручную коррекцию.
- Хранилище: SQLite с `WAL`, миграциями (Alembic или эквивалент); сырой GSI оставлять в `.jsonl.gz` формата базового проекта, аналитические факты — в SQLite.
- Подключения: Jev по официальному `systemone` API, Groq через совместимый с OpenAI chat-completions endpoint, DeepSeek через официальный API. Базовый алгоритм работает без ключей и интернета, используя последний валидный snapshot.
- Секреты: Windows DPAPI/keyring либо строго локальный защищённый механизм; `.env` только для разработки, в `.gitignore`; UI никогда не возвращает ключ, только `configured=true/false`. Запрет логирования ключей и сырых заголовков авторизации.
- Packaging: сначала `run.cmd` базового проекта; затем один локальный инсталлятор/архив. Проверить реальную совместимость с Windows 10. Не рассчитывать на `d2bg window` как готовую возможность: в проверенной ревизии README её описывает, но файл `src/d2bg/window.py` отсутствует — нужен audit/реализация.

## 4. Архитектура и контракты

```text
Dota 2 --GSI--> GSI parser --> GameStateNormalizer --> EventBus --> Recorder/SQLite
                    |                                  |
Visible draft --CV--> DraftObservation ----------> StateFusion
OpenDota / snapshots ---------------------------------|
                                                       v
                            Rules+Stats CandidateGenerator
                                                       |
                             +-------------------------+-------------------+
                             |                         |                   |
                          Jev Choice               Groq Advisor      Offline rules
                             |                         |                   |
                             +--------------------> Validator <------------+
                                                       |
                                            Recommendation + Evidence
                                                       |
                                       /compact UI + optional overlay
                                                       |
                                               DecisionJournal
                                                       |
                        OpenDota parsed match + local GSI --> FeatureExtract
                                                       |
                                          DeepSeek PostMatch Analyst
                                                       |
                                          Findings/Goals/History
```

**Один источник правды:** нормализованный `GameContext` с полями `match_id`, `patch`, `phase`, `time_s`, `hero_id`, `position`, `level`, `available_skill_points`, `learned_skills`, `allies`, `enemies_visible`, `draft_confidence`, `inventory`, `stash`, `gold`, `buyback_cost`, `gpm`, `xpm`, `last_hits`, `data_age_s`, `evidence_ids` и source-меткой каждой группы полей (`gsi`, `cv`, `opendota`, `manual`, `unknown`). Не выдавать неизвестные данные за доступные.

Поля должны быть optional, события идемпотентными. Различать время игры и системное время. Не записывать необработанные ключи GSI auth в логи. При смене `match_id` сбрасывать match-state, сохраняя историю в БД. После старта приложения посреди матча корректно восстанавливать snapshot по первым GSI-событиям.

**Типы решений:** `PICK_HERO`, `SKILL_LEVEL`, `TALENT`, `ITEM_NEXT`, `ITEM_SITUATIONAL`, `ITEM_BUYBACK_GUARD`, `POSTMATCH_FINDING`. Каждый `Recommendation` содержит `id`, `match_id`, `game_time_s`, `type`, `candidate_id`, `alternatives[]`, `reason_ru`, `source`, `confidence` (если провайдер даёт), `confidence_kind`, `evidence_ids[]`, `context_hash`, `model_version`, `data_patch`, `status` (`suggested | seen | dismissed | followed | unknown | expired`) и `expires_at`. Confidence модели **не** трактовать как вероятность победы или истинность решения.

## 5. Функциональные требования

### F1. Подключение Dota 2 (P0)
1. Переиспользовать установщик GSI, parser, recorder, демо-матч, health и setup-страницу d2bg. Единственный конфиг приложения в `game/dota/cfg/gamestate_integration/`.
2. В UI показывать `connected`, время последнего GSI, матч, патч, версию snapshot, доступные поля, ошибки и устаревшие данные.
3. Система должна работать без игры на демо/GSI replay, в том числе без облачных ключей.
4. Не начинать внешние AI-запросы на каждый GSI tick; использовать debounce/event triggers.

### F2. Драфт (P0)
1. Интегрировать `DraftWatcher`/`recognizer` Dota Assist в отдельный `DraftCVAdapter`, вывод `ally_ids[]`, `enemy_ids[]`, `banned_ids[]`, `unknown_slots`, `confidence`, `capture_resolution`, `timestamp`.
2. Передавать распознанные id в существующий `draft.service.analyze`. Позиция 1–5 и личный пул управляются в интерфейсе; учитывать баны и занятых героев.
3. Если распознавание неуверенное — явно показывать `?` и разрешать корректировать вручную. **Никакой автоподстановки неизвестных героев**.
4. В обычном Ranked All Pick GSI не раскрывает полный драфт врагов. Не использовать spectator-only поля как будто они доступны игроку.
5. Выводить топ-5 с причиной (мета, враги, союзники, личный пул) и оценкой достаточности данных. Не заявлять процент победы как факт.

### F3. Прокачка (P0)
1. Брать базовую последовательность из `builds/guide.py` и профессиональных данных по **герою + позиции** (если есть), учитывать текущий изученный набор и доступные очки.
2. Точно проверять, можно ли повысить способность/талант на данном уровне, нет ли уже максимального ранга, как учитывать врождённые способности. При неопределённости — не придумывать доступность.
3. Показывать «Следующая способность: Q / W / E / R» + визуальный порядок + краткую причину; после фактической прокачки обновлять состояние.
4. При небольшом pro sample или отсутствии данных переходить к baseline/ручному выбору и предупреждать, а не симулировать уверенность.

### F4. Предметы и Quickbuy (P0)
1. Использовать `next_items`, owned-components и `situational_items` из d2bg; дополнить подходящими предметными правилами OHA **после портирования и тестирования**.
2. Разделять **Core**, **Situational**, **Defensive**, **Buyback safety**. Исключать уже собранное и взаимоисключающие варианты (например, дубли улучшенных ботинок), считать реальные недостающие компоненты и золото.
3. Считать ETA при текущем GPM с пометкой, что это ориентир; не предлагать замену предмета только из-за кратковременного изменения показателей.
4. Для предмета показывать причины против конкретных **известных по драфту** героев, текущую экономику и альтернативы. Не использовать тайно невидимые в игре предметы противника.
5. Кнопка «Показать в игровом магазине / как поставить в Quickbuy» — только UI-инструкция или нативный гайд, **без генерации мышиных событий**. Штатный Mark for Buy пользователь настраивает сам.

### F5. Jev + Groq: агент, не генератор случайных ответов (P1)
1. Сделать интерфейс `DecisionProvider`: `baseline`, `jev`, `groq`, `hybrid`, с конфигурацией и `FeatureFlags`; поставка без ключей обязана работать на baseline.
2. Сначала `CandidateGenerator` формирует допустимые варианты. Jev получает **только кандидатные id, актуальный patch и компактный GameContext**, использует `choice/score/noul` (по реальной схеме официальной документации). Запрещено передавать Jev доступ к исполнению системных команд.
3. Groq LLM Advisor вызывается **не на каждый tick**, а при событиях: сильная неоднозначность, изменение состава, важный талант, смена ветки предметов, запрос игрока. Возвращает структурированные рекомендации по JSON Schema/Pydantic. При отсутствии schema-режима используемой модели — парсинг JSON + валидация + контролируемый retry.
4. `HybridPolicy`: baseline даёт безопасный порядок; Jev предлагает rerank; Groq добавляет аргументы или предлагает альтернативу; Validator в последнюю очередь проверяет допустимость, наличие данных и легальность действия. Никакая модель не может обойти Validator.
5. Если модели противоречат: не скрывать конфликт, показывать baseline + краткое «есть альтернативная рекомендация». При ошибке/таймауте/429/402 — работать автономно, без зависаний UI. Кэшировать по `context_hash` и version/patch.
6. Ограничить расходы настройками: по умолчанию не более **20 Jev** и **5 Groq** обращений на матч, а DeepSeek — один отчёт после матча; лимиты регулируются пользователем, UI показывает приблизительную стоимость и расход токенов. Это стартовые настройки, не ограничения провайдеров.
7. Секреты вводятся только пользователем локально. Тесты должны мокать все платные API. Никакого автоматического real API smoke test в CI.

### F6. Post-match аналитика (P0 базовая, P1 AI)
1. Переиспользовать `matches/postgame.py`, `matches/review.py` и `profile/analytics.py`. После матча получить статистику из OpenDota, связать её с собственными GSI-записями и рекомендациями по `match_id`/таймкодам. Запрос парсинга — только с учётом opt-in/лимитов.
2. Сначала детерминированный отчёт: KDA, GPM/XPM, LH@10, тайминги ключевых предметов относительно **актуальных** pro-данных, смерти по минутам, моменты прокачки, эффективность закупа, байбэк, доступные события. Сравнения стратифицировать по герою, позиции, патчу и, где возможно, рейтингу.
3. Факты отдельно от интерпретаций. Каждая находка содержит `event_time_s`, `metric`, `actual`, `baseline`, `comparison_group`, `evidence_ids[]`, `certainty` (`verified | likely | insufficient_data`), `review_anchor`, `recommendation`.
4. DeepSeek получает **отобранные факты/аномалии**, журнал рекомендаций и минимальные контексты эпизодов, но не весь сырой реплей. Возвращает JSON `summary`, `strengths[]`, `findings[]`, `practice_goals[]`, `unknowns[]` и `model_version`. Строгая Pydantic-валидация; несуществующие `evidence_ids` блокировать.
5. Не утверждать причинность по одной корреляции («ты проиграл из-за предмета»). Например, смерть перед Рошаном — повод исследовать таймкод, но не автоматически доказанная ошибка. Если OpenDota не разобрал матч — дать частичный отчёт с явным списком отсутствующих данных.
6. В отчёте показывать **ошибки пользователя и ошибки агента**: совет был дан/показан, что игрок купил/прокачал, что произошло позже; не приписывать агенту causal winrate. Оценки давать с маркировкой уверенности.
7. Память: агрегировать повторяющиеся проблемы за 5/10/20 матчей; после каждой игры сохранять максимум 1–3 практические цели; отслеживать тренды без недостоверных прогнозов MMR.
8. Глубокие replay-события из `.dem` — опциональный P2; локальный Java-парсер запускать только по запросу и изолировать от обычного UI.

### F7. Интерфейс (P0/P1)
- Использовать текущий React UI d2bg, сохранить `Live`, `Draft`, `Heroes`, `Items`, `Matches`, `Setup`.
- Добавить `Copilot` (основная рекомендация, уровень уверенности/возраст данных, альтернативы, кнопка скрыть), `Review` (таймлайн и личный план) и `Providers` (Jev/Groq/DeepSeek, расходы, online/offline).
- `/compact`: 320–420px по ширине для второго экрана: следующий скилл, следующий предмет, 1–2 причины, недостающее золото, статус моделей.
- Полупрозрачный always-on-top поверх Borderless — отдельная **P2-функция** после проверки Windows 10; сначала реализовать в браузере/на втором мониторе. Оверлей должен быть click-through вне режима настройки и не закрывать элементы Dota.
- UI должен позволять скрыть/выключить каждую категорию подсказок, отключить звук, зафиксировать режим только локальных правил, указать бюджет и удалить историю.

## 6. API, структуры данных и БД

Переиспользовать текущие маршруты FastAPI; новые добавлять только после аудита существующих, чтобы не плодить дубликаты. Ориентировочные новые маршруты:

```text
GET  /api/copilot/status              # GSI, патч, providers, отставание данных
GET  /api/copilot/recommendations     # последние валидные рекомендации
GET  /api/copilot/stream              # SSE: state/recommendations/events
POST /api/copilot/draft/manual        # исправление CV драфта
GET  /api/copilot/matches/{id}/review # детерминированная и AI-аналитика
POST /api/copilot/matches/{id}/analyze# явный запуск/повторный разбор
GET  /api/copilot/goals               # повторяющиеся ошибки и цели
POST /api/copilot/providers/test      # отдельное тестирование по кнопке
```

Пример **внутреннего** решения (не провайдерский wire-format):

```json
{
  "match_id": "demo-001",
  "time_s": 1160,
  "type": "ITEM_NEXT",
  "candidate_id": "black_king_bar",
  "alternatives": ["manta", "sange_and_yasha"],
  "source": "hybrid",
  "reason_ru": "Возможный защитный приоритет против открытого контроля врагов",
  "confidence": null,
  "confidence_kind": "unverified_model_score",
  "evidence_ids": ["draft:lion", "inventory:power_treads", "build:juggernaut-pos1"],
  "data_patch": "from_snapshot",
  "status": "suggested"
}
```

SQLite-сущности: `matches`, `gsi_events_index` (пути и таймкоды без дублирования гигабайт), `draft_observations`, `recommendations`, `provider_calls` (latency/tokens/cost/status без ключей), `postmatch_metrics`, `postmatch_findings`, `practice_goals`, `feature_flags`. Индексы по `match_id`, `game_time_s`, `type`, `created_at`. Схема с миграциями и retention policy (по умолчанию GSI записи хранятся для последних 20 матчей, аналитика сохраняется пока игрок не удалит).

## 7. Триггеры, ресурсы и отказоустойчивость

- Пересчёт локальных советов по событию `draft_changed`, `hero_selected`, `skill_point_gained`, `skill_leveled`, `item_changed`, `gold_threshold_crossed`, `phase_changed`, `death/respawn`, `match_finished`; дебаунс 0.3–1 с.
- Не отправлять сырые скриншоты в облако по умолчанию; Jev/Groq/DeepSeek получают только отобранные структурированные игровые факты. Показывать список отправляемых полей и возможность отключить outbound.
- Ограничивать свежесть: после потери GSI >30 секунд показать `stale` и прекратить выдавать новые динамические рекомендации; предыдущие — только с пометкой.
- Максимальное ожидание внешнего решения задаётся config, таймаут не блокирует UI и не задерживает локальный baseline. Использовать backoff для 429/529, circuit breaker и offline fallback для 402/401/5xx.
- После обновления Dota-патча snapshot помечать устаревшим, отключать высокоуверенные формулировки и предлагать ручное обновление данных. Не переобучать модели автоматически без проверок.
- Измерять latency, rate, cost, conflicts, parse-error и отказ GSI; графики и экспорт диагностики без чувствительных данных.

## 8. Проверки и критерии приёмки

**Обязательно:**
1. На чистой Windows 10 приложение стартует с `run.cmd`, открывает UI, запускает демо без запущенной Dota и без API-ключей. Все исходные проверки d2bg v2 продолжают проходить (`uv run pytest`, `ruff`, `mypy`, `npm run build` и тесты frontend — проверить команды в `Makefile`).
2. Установка GSI создаёт единственный cfg; удаление убирает только свой cfg. Токены и ключи не отражаются в логах и ответах UI.
3. 20+ тестовых GSI fixtures покрывают старт посреди матча, уровень/скилл, изменение предметов, потерю пакетов, окончание матча; локальные рекомендации воспроизводимы после replay JSONL.
4. CV-тесты на 50+ снимках разного разрешения/UI/скинов: неизвестные пики остаются неизвестными; неверное распознавание нельзя автоматически подать как достоверное. Не нужно обещать определённый процент точности без собственного замера.
5. Не менее 100 вручную размеченных игровых ситуаций и unit tests: контроль/урон, нет доступных скиллов, недостаток золота, байбэк, дубли предметов, редкий герой, устаревший патч. Нулевое число **недопустимых действий** в тестовом наборе.
6. Provider tests: 401, 402, 429, 5xx, timeout, невалидный JSON, устаревший ответ и конфликт Jev/Groq — baseline продолжает работать, без ошибок UI.
7. Отчёт для тестового match ID содержит проверяемые метрики и хотя бы одну находку с `evidence_ids` или честную отметку `insufficient_data`; повторный запуск не создаёт дублей. При отсутствии разобранного реплея отчёт частичный.
8. Security/static check отклоняет импорт инструментов чтения памяти и генерации игровых нажатий (`pymem`, `pyautogui`, `pynput`, `keyboard`, `ReadProcessMemory`, DLL-injection и т. п.) в production-коде; никаких фактических автонажатий в обычной игре.
9. UI фиксирует состояние `no_data`, `low_confidence`, `offline`, `stale`, `awaiting_parse`; русский интерфейс работает на двух мониторах. Запрещены немаркированные демонстрационные данные в реальном режиме.

**Ориентиры производительности** (проверить замерами на целевой машине, не трактовать как гарантии сторонних API): локальная выдача после события ≤500 мс p95; GSI обработка без зависаний; после `skill_point_gained` рекомендация baseline отображается без ожидания сетевого вызова; облачные ответы могут прийти позже и не должны мигать/переписывать уже выполненное действие.

## 9. Поэтапное выполнение и deliverables

**Этап 0 — аудит и создание основы.** Сделать fork/рабочую копию d2bg v2; зафиксировать SHA, сохранить `LICENSE`; проверить `run.cmd`, тесты, GSI demo и /compact; изучить текущие API/схемы. Создать `docs/ARCHITECTURE.md`, `THIRD_PARTY_NOTICES.md`, `docs/IMPLEMENTATION_PLAN.md`. Исправить README-несоответствия только после проверки. **Результат:** запускается оригинальное приложение + задокументированы реюз и границы.

**Этап 1 — единый контекст и журнал.** GameContext/EventBus/SQLite, нормализованный источник GSI, модель рекомендаций, запись и воспроизведение решений. **Результат:** тестовые события проходят через pipeline и сохраняются без AI.

**Этап 2 — базовый Copilot.** Рекомендации скиллов и предметов + Quickbuy-инструкция, buyback guard, `/compact`, безопасный baseline. **Результат:** работает полностью офлайн на демонстрационном матче.

**Этап 3 — драфт CV.** Адаптер Dota Assist; ручная коррекция, распознавание только видимой области, confidence/evidence и переиспользование draft-service. **Результат:** real/saved screenshot даёт контролируемые рекомендации.

**Этап 4 — облачные провайдеры.** Jev Choice/Score/Noul + Groq Advisor с Pydantic-валидатором, политикой hybrid, таймаутами, кэшем, лимитами стоимости и полностью замоканными тестами. **Результат:** можно переключаться между baseline/Jev/Groq/hybrid; без ключей поведение не ломается.

**Этап 5 — послематчевый тренер.** OpenDota postgame, свои журналы, детерминированные findings, DeepSeek для качественных объяснений, личные цели и отчёт с таймкодами. **Результат:** импорт тестового match ID, сохранение отчёта, повторяемая аналитика без выдуманных событий.

**Этап 6 — UX и сборка.** Настройки/отключение облака, Windows 10 QA, диагностический экспорт, инсталлятор. Опциональный always-on-top и локальный `.dem` parser — только отдельными PR, не блокируют MVP.

После **каждого** этапа выдать: изменённые файлы, короткое объяснение архитектурного решения, какие части открытого кода переиспользованы, команды запуска, фактические результаты тестов и известные ограничения. Не объявлять задачу «готово», пока минимальный сценарий не показан на demo/GSI replay.
